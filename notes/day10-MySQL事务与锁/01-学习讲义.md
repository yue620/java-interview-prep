## 一、事务与 ACID

**事务：一组 SQL 要么全部成功，要么全部失败。** 转账是永远的例子。

| 特性 | 含义 | 靠什么实现 |
|---|---|---|
| **A 原子性** | 要么全做，要么全不做 | **undo log**（回滚日志，记录"怎么撤销"） |
| **C 一致性** | 数据从一个正确状态到另一个正确状态（A+100 必对应 B-100） | 由 A+I+D 共同保证的最终目标 |
| **I 隔离性** | 并发事务互相不干扰 | **MVCC + 锁**（今天的主角） |
| **D 持久性** | 提交了就永远不丢 | **redo log**（重做日志，先写日志再刷盘） |

> 加分回答："原子性靠 undo log，持久性靠 redo log，隔离性靠 MVCC 和锁，一致性是前三者保障的目标。"

## 二、并发下的三种怪现象 ⭐必考

两个事务同时操作同一条数据，如果不加控制：

| 现象 | 人话解释 | 例子 |
|---|---|---|
| **脏读** | 读到了别人**还没提交**的数据 | 别人改了一半回滚了，你读到的是"假数据" |
| **不可重复读** | 同一次事务里，**同一行**读两遍结果不一样（被别人改并提交了） | 第一次读库存 10，第二次读变 5 |
| **幻读** | 同一次事务里，**同一个范围查询**查两遍，多出了新行（被别人插入并提交了） | 第一次查 3 个商品，第二次查变 4 个 |

> 记忆口诀：**脏读 = 读了没提交的；不可重复读 = 同一行变了（update）；幻读 = 行数变了（insert/delete）。**

## 三、四种隔离级别 ⭐必考

从宽松到严格，性能从高到低：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 谁在用 |
|---|---|---|---|---|
| 读未提交 READ UNCOMMITTED | ❌ 有 | ❌ 有 | ❌ 有 | 没人用 |
| **读已提交 READ COMMITTED** | ✅ 解决 | ❌ 有 | ❌ 有 | Oracle 默认、互联网常用 |
| **可重复读 REPEATABLE READ** | ✅ 解决 | ✅ 解决 | ✅ 基本解决（InnoDB 用临键锁防住） | **MySQL InnoDB 默认** |
| 串行化 SERIALIZABLE | ✅ 解决 | ✅ 解决 | ✅ 解决 | 完全排队执行，性能差 |

```sql
-- 查看和设置隔离级别
SELECT @@transaction_isolation;
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

> 必背：**MySQL 默认 REPEATABLE READ（可重复读）**。追问"既然默认 RR 为什么互联网公司爱用 RC"：RC 下锁更少（无间隙锁）、并发度更高、binlog 配合更好。

## 四、MVCC：不加锁的并发控制 ⭐⭐高频

**问题**：RR 级别下"读"如果靠加锁实现，读写互相阻塞，性能完蛋。InnoDB 的方案是 **MVCC（多版本并发控制）**：同一行数据保留多个版本，读操作读"快照"，不加锁。

### 三个组成部分

**① 隐藏列**：每行数据除了你的字段，还有：
- `DB_TRX_ID`：最后修改这行的事务 ID
- `DB_ROLL_PTR`：回滚指针，指向 undo log 里的上一个版本

**② undo log 版本链**：每次 update，旧版本存进 undo log，用回滚指针串成链：

```
当前行 (trx_id=105) → undo log 旧版本 (trx_id=102) → 更旧版本 (trx_id=100)
```

**③ ReadView（读视图）**：事务执行 SELECT 时拍的一张"活跃事务快照"，记录"当前有哪些事务还没提交"。

### 判断规则（能讲出大意即可）

拿到一行数据，看它的 `DB_TRX_ID`：
- 是**自己**改的 → 可见
- 该事务在 ReadView 生成前**已提交** → 可见
- 该事务还**没提交**或在 ReadView 之后才开始的 → **不可见，顺 undo log 链找下一个版本**，直到找到可见的

### 两种隔离级别的差别就在 ReadView 生成的时机 ⭐

- **READ COMMITTED**：**每次 SELECT** 都生成新 ReadView → 能读到别人刚提交的 → 不可重复读
- **REPEATABLE READ**：**只在第一次 SELECT 时**生成 ReadView，之后复用 → 事务期间读到的永远是同一快照 → 可重复读

> 一句话总结 MVCC：**通过 undo log 版本链 + ReadView，让读操作读历史快照，实现读写不加锁、互不阻塞。**

## 五、锁：管"写 vs 写"和"写 vs 读当前数据"

MVCC 管快照读（普通 SELECT），但 UPDATE/DELETE/`SELECT ... FOR UPDATE`（当前读）还是要加锁。

| 锁 | 作用范围 | 场景 |
|---|---|---|
| **行锁（Record Lock）** | 锁索引上的一条记录 | `UPDATE ... WHERE id=1` |
| **间隙锁（Gap Lock）** | 锁索引记录之间的"空隙"，防止插入 | RR 级别防幻读 |
| **临键锁（Next-Key Lock）** | 行锁 + 间隙锁，左开右闭区间 | **InnoDB RR 级别默认加锁单位** |

> 关键提醒：InnoDB 行锁是**加在索引上的**！`UPDATE ... WHERE name='A'`（name 无索引）会**锁全表** —— 这就是"索引没建好导致全表锁"的经典事故。

**悲观锁 vs 乐观锁**（应用层概念，面试高频）：

```java
// 悲观锁：先锁住再操作（悲观地认为一定会冲突）
// SELECT stock FROM product WHERE id=1 FOR UPDATE;  （数据库行锁）

// 乐观锁：不加锁，更新时检查"数据被别人动过吗"（version 版本号 / CAS）
// UPDATE product SET stock = stock - 1, version = version + 1
// WHERE id = 1 AND version = 3;   // version 变了说明有人动过 → 更新失败重试
```

JPA 里加 `@Version` 注解字段就自动实现乐观锁（ISSUE-009 会亲手用）。

## 六、超卖问题（串联今天所有知识的场景题）⭐

库存只剩 1 件，100 个人同时下单，代码不加控制：

```
线程A：读库存 = 1，判断 > 0，通过
线程B：读库存 = 1，判断 > 0，通过（A 还没扣减）
A 扣减：stock = 0；B 扣减：stock = -1  ← 超卖！
```

解决路线（从弱到强，也是面试回答的层次感）：

1. **乐观锁**：`UPDATE ... SET stock=stock-1 WHERE id=? AND stock>0`，用 SQL 原子性兜底（影响行数=0 则失败）
2. **悲观锁**：`SELECT ... FOR UPDATE` 先锁行
3. **Redis 预减库存 + 分布式锁**（Day 11 讲，高并发场景正解）
