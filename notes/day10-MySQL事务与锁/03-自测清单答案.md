# Day 10 自测清单答案（采分点版）

**1. ACID + 实现**
- **A 原子性**：全做或全不做，靠 **undo log**
- **C 一致性**：数据从一种正确状态到另一种，是 A/I/D **共同保证的目标**
- **I 隔离性**：并发事务互不干扰，靠 **MVCC + 锁**
- **D 持久性**：提交后永不丢失，靠 **redo log**（先写日志再刷盘，WAL）

**2. 三种读现象**
- **脏读**：读到别人**未提交**的数据（后回滚了，读到假的）
- **不可重复读**：同事务两次读**同一行**不一样（别人 update 并提交）
- **幻读**：同事务两次**范围查询行数**不一样（别人 insert/delete 并提交）

**3. 四种隔离级别**
- 读未提交：都不解决
- **读已提交 RC**：解决脏读（Oracle 默认）
- **可重复读 RR**：解决脏读+不可重复读，InnoDB 靠临键锁**基本解决幻读**——**MySQL 默认**
- 串行化：全解决，完全排队，性能差

**4. RR 改 RC 的理由**
- RC **没有间隙锁**，锁冲突少、并发度高；死锁概率低；配合 row 格式 binlog 数据一致性有保障

**5. MVCC 三件套**
- MVCC = 多版本并发控制：同一行保留多版本，**读快照不加锁，读写互不阻塞**
- 组成：① 隐藏列（**DB_TRX_ID** 最近修改事务 ID、**DB_ROLL_PTR** 回滚指针）② **undo log 版本链** ③ **ReadView**（活跃事务快照）
- 判断：行的 trx_id 是自己/已提交 → 可见；未提交/太晚开始 → 沿 undo 链找旧版本

**6. ReadView 时机差异**
- RC：**每次 SELECT 重新生成** → 能读到别的事务新提交的数据 → 不可重复读
- RR：**第一次 SELECT 生成后复用** → 整个事务读同一快照 → 可重复读
- 这是 RC 与 RR 行为差异的**根因**

**7. 三种锁**
- 行锁：锁**一条索引记录**
- 间隙锁：锁索引记录间的**空隙**，禁止插入（防幻读）
- 临键锁：**行锁+间隙锁**（左开右闭），是 InnoDB RR 的**默认加锁单位**

**8. WHERE 不走索引的后果**
- InnoDB 行锁**加在索引上**；条件没走索引就只能**全表扫描并锁住所有行**（相当于锁全表），并发直接崩。生产事故高发点

**9. 悲观锁 vs 乐观锁**
- 悲观锁：认为**一定会冲突**，先加锁再操作（`SELECT ... FOR UPDATE`、synchronized）
- 乐观锁：认为**一般不冲突**，操作时不加锁，提交时用**版本号/CAS** 校验"数据有没有被别人动过"
- 实现：`version` 字段，`UPDATE ... SET version=version+1 WHERE id=? AND version=旧值`，影响行数 0 则重试；JPA 用 `@Version` 自动实现

**10. 超卖场景（满分框架）**
- 发生：读库存和扣库存**不是原子的**，并发下两个线程都读到 1，都通过判断 → 库存扣成 -1
- 方案（按层次答）：
  ① 数据库乐观锁：`UPDATE product SET stock=stock-1 WHERE id=? AND stock>0`，一条 SQL 原子完成，影响行数 0 = 抢完
  ② 悲观锁：`SELECT ... FOR UPDATE`
  ③ 高并发正解：**Redis 原子预减库存（DECR/Lua）+ 消息队列削峰 + 数据库最终落库**（Day 11-12 展开）

## 满分口述模板（第 5、6 题合并版）

"MVCC 是 InnoDB 解决读写并发的方案，核心思想是读操作读快照不加锁。它由三部分组成：每行有两个隐藏列——最近修改它的事务 ID 和指向 undo log 的回滚指针；每次修改会把旧版本存入 undo log 形成版本链；事务查询时生成 ReadView，记录当前活跃未提交的事务集合。拿到一行数据后比对事务 ID，不可见就沿 undo log 找旧版本。RC 和 RR 的区别就在 ReadView 的生成时机：RC 每次查询都生成新的，所以能读到别人刚提交的；RR 只在第一次查询生成并复用，所以整个事务读到的是同一快照，实现了可重复读。"
