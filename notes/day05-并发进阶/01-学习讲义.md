## 一、为什么需要线程池

### 1.1 没有池的问题

```java
// 每来一个任务就 new 一个线程
for (int i = 0; i < 1000; i++) {
    new Thread(() -> 干活()).start();
}
```

问题有两个：

1. **线程创建/销毁很贵**（要和操作系统打交道），1000 个任务创建 1000 个线程，开销巨大
2. **线程数量失控**，任务一多就把内存和 CPU 拖垮（一个线程默认栈约 1MB，1000 个就是 1G）

### 1.2 池化思想：养几个固定员工，轮流接活

线程池 = **固定数量的线程（员工）+ 一个任务队列（待办清单）**。任务来了扔进队列，空闲员工从队列取活干，干完取下一件——**线程被复用，数量可控**。

**示例 1：第一个线程池**

```java
import java.util.concurrent.*;

public class PoolDemo {
    public static void main(String[] args) {
        ExecutorService pool = Executors.newFixedThreadPool(2);  // 养 2 个员工

        for (int i = 0; i < 5; i++) {          // 5 个任务
            int taskId = i;
            pool.submit(() -> {
                System.out.println(Thread.currentThread().getName()
                        + " 执行任务 " + taskId);
            });
        }

        pool.shutdown();   // 不再接新任务，干完手里的活就关门
    }
}
```

输出（注意：**5 个任务只由 2 个线程轮流完成**）：

```
pool-1-thread-1 执行任务 0
pool-1-thread-2 执行任务 1
pool-1-thread-1 执行任务 2
pool-1-thread-2 执行任务 3
pool-1-thread-1 执行任务 4
```

## 二、线程池 7 个参数（必考中的必考）

`ThreadPoolExecutor` 的完整构造：

```java
new ThreadPoolExecutor(
    2,                              // ① corePoolSize：核心线程数（正式员工）
    4,                              // ② maximumPoolSize：最大线程数（正式+临时工）
    60L, TimeUnit.SECONDS,          // ③④ 临时工空闲多久被辞退（keepAliveTime + 单位）
    new LinkedBlockingQueue<>(10),  // ⑤ workQueue：任务队列（待办清单容量 10）
    Executors.defaultThreadFactory(),        // ⑥ threadFactory：线程工厂（怎么创建线程，可用来起名字）
    new ThreadPoolExecutor.AbortPolicy()     // ⑦ handler：拒绝策略（清单满了、人也满了，新任务怎么办）
);
```

### 2.1 任务进入线程池的流程（必考，能画图）

```
任务进来
  │
  ▼
当前线程数 < corePoolSize？ ──是──→ 直接开新线程执行
  │否
  ▼
队列没满？ ──是──→ 进队列排队，等核心线程来取
  │否（队列满了）
  ▼
当前线程数 < maximumPoolSize？ ──是──→ 开"临时工"线程执行
  │否
  ▼
执行拒绝策略（⑦）
```

**口诀**：**先加满正式员工 → 再排队 → 队满招临时工 → 临时工也满了才拒绝**。

> ⚠️ 反直觉点：不是"线程数到 core 就招临时工"，而是**先排队，队满了才招临时工**。很多人背错顺序。

### 2.2 四种拒绝策略

| 策略 | 行为 | 场景 |
|---|---|---|
| **AbortPolicy**（默认） | 抛 `RejectedExecutionException` | 通用，让调用方感知失败 |
| CallerRunsPolicy | **让提交任务的线程自己跑**这个任务 | 变相"减速"，不丢任务 |
| DiscardPolicy | 悄悄丢掉新任务 | 允许丢的日志类任务 |
| DiscardOldestPolicy | 丢掉队列里**最老**的任务，再试提交 | 新任务更重要的场景 |

**示例 2：亲手触发拒绝策略**

```java
import java.util.concurrent.*;

public class RejectDemo {
    public static void main(String[] args) {
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
                1, 1,                          // 只要 1 个员工，不招临时工
                0L, TimeUnit.SECONDS,
                new LinkedBlockingQueue<>(2),  // 队列只排 2 个
                new ThreadPoolExecutor.AbortPolicy());

        try {
            for (int i = 0; i < 5; i++) {      // 提交 5 个任务：1 个在跑 + 2 个排队 + 第 4 个被拒
                int id = i;
                pool.submit(() -> {
                    try { Thread.sleep(1000); } catch (InterruptedException e) { }
                    System.out.println("执行 " + id);
                });
                System.out.println("提交任务 " + id + " 成功");
            }
        } catch (RejectedExecutionException e) {
            System.out.println("💥 任务被拒绝: " + e.getMessage());
        }
        pool.shutdown();
    }
}
```

输出（第 4 个任务（id=3）触发拒绝）：

```
提交任务 0 成功
提交任务 1 成功
提交任务 2 成功
💥 任务被拒绝: Task ... rejected from ...
```

### 2.3 为什么不推荐 Executors 的快捷方法（阿里规范，高频）

```java
Executors.newFixedThreadPool(n)      // ⚠️ 队列是 LinkedBlockingQueue，容量 Integer.MAX_VALUE ≈ 无界
Executors.newCachedThreadPool()      // ⚠️ maximumPoolSize = Integer.MAX_VALUE ≈ 线程数无上限
```

任务激增时：前者队列无限长 → OOM；后者线程无限创建 → OOM。**阿里巴巴开发规范明确禁止**，要求手动 new ThreadPoolExecutor，把 7 个参数写明白。

## 三、CAS 与原子类（回忆 Day 1 的 ConcurrentHashMap）

### 3.1 CAS 再认识

**CAS = Compare And Swap**，一条 CPU 原子指令：

> "我认为这个位置的值是 A，如果是，就改成 B；如果不是（被人动过），就失败重来。"

Java 里 `AtomicInteger` 就是靠它实现的：

```java
AtomicInteger count = new AtomicInteger(0);
count.incrementAndGet();   // 内部：CAS 循环重试，直到成功，全程无锁
```

### 3.2 示例 3：三种方式修"账本"（呼应 Day 3 示例 5）

```java
import java.util.concurrent.atomic.AtomicInteger;

public class AtomicDemo {
    static int unsafeCount = 0;
    static int syncCount = 0;
    static AtomicInteger atomicCount = new AtomicInteger(0);

    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> {
            for (int i = 0; i < 10000; i++) {
                unsafeCount++;                 // 方式①：裸奔
                synchronized (AtomicDemo.class) { syncCount++; }  // 方式②：加锁
                atomicCount.incrementAndGet(); // 方式③：CAS 原子类
            }
        };
        Thread t1 = new Thread(task);
        Thread t2 = new Thread(task);
        t1.start(); t2.start();
        t1.join();  t2.join();

        System.out.println("裸奔:        " + unsafeCount);   // 不到 20000
        System.out.println("synchronized: " + syncCount);     // 20000
        System.out.println("AtomicInteger:" + atomicCount);   // 20000
    }
}
```

### 3.3 CAS 的两个坑（面试追问）

1. **ABA 问题**：值从 A→B→A 变回去，CAS 只看"现在是不是 A"发现不了中间变化。解决：`AtomicStampedReference`（带版本号，比较"值+版本"）
2. **自旋开销**：竞争激烈时 CAS 反复失败重试，空转耗 CPU。高竞争计数场景用 `LongAdder`（分段思想：多个计数单元分散竞争，最后求和）

## 四、ThreadLocal：每个线程的"私人储物柜"

### 4.1 一句话理解

普通变量是所有线程**共享**的；ThreadLocal 变量是**每个线程一份私有副本**——线程 A 存的值，线程 B 根本看不到。

```java
ThreadLocal<String> holder = new ThreadLocal<>();

holder.set("A的东西");   // 线程 A 里调用：只有 A 能拿到
holder.get();            // 拿自己的那份
holder.remove();         // ⚠️ 用完必须删！（见下）
```

**典型用途**：存"当前登录用户"、"当前请求 traceId"、SimpleDateFormat（线程不安全，每个线程一份）。Spring 的 @Transactional、MDC 日志链路底层都是 ThreadLocal。

### 4.2 内存泄漏陷阱（必考）

ThreadLocal 的内部结构：`Thread` 对象里有个 Map，**key 是 ThreadLocal（弱引用），value 是强引用**。

```
GC 时：key（弱引用）被回收 → key 变成 null
       value（强引用）还在 → 但这个 value 永远拿不到了（key 没了）
       → value 泄漏在内存里
```

**解法**：用完调 `remove()`。尤其在线程池里——线程是复用的，不删的话下一个任务会读到上一个任务遗留的值（**脏数据** + 泄漏双重问题）。

## 五、AQS 简介（知道是什么即可，不深究）

**AQS（AbstractQueuedSynchronizer，队列同步器）** = Java 并发包的"地基"。ReentrantLock、Semaphore、CountDownLatch 底层都是它。

核心思想一句话：

> **一个 volatile int state（锁的"状态"）+ 一个 FIFO 等待队列**。抢锁 = CAS 改 state；抢不到 = 进队列排队阻塞；释放 = 唤醒队首。

面试问到这个层次够用了："ReentrantLock 底层是 AQS，AQS 用 volatile state + CAS 管理锁状态，抢不到的线程进 CLH 队列阻塞，释放时唤醒队首。"

## 六、本日知识地图

```
线程池
├── 为什么：线程创建贵 + 数量要可控 → 复用固定线程
├── 7 参数：core / max / keepAlive+单位 / workQueue / threadFactory / handler
├── 流程：先满核心 → 再排队 → 队满招临时工 → 都满才拒绝（顺序别背错！）
├── 拒绝策略：Abort(抛异常默认) / CallerRuns(谁提交谁跑) / Discard / DiscardOldest
└── Executors 快捷方法禁用：Fixed 队列无界、Cached 线程无上限 → OOM

CAS / 原子类
├── CAS：CPU 原子指令"比较并交换"，失败自旋重试，无锁
├── AtomicInteger：CAS 实现，修复 count++ 竞态
└── 坑：ABA（→AtomicStampedReference）、高竞争自旋耗 CPU（→LongAdder）

ThreadLocal
├── 每线程一份私有副本：存当前用户/traceId/SimpleDateFormat
└── 陷阱：key 弱引用 value 强引用 → 内存泄漏；线程池复用 → 脏数据。用完必须 remove()

AQS（了解）
└── volatile state + CAS + FIFO 队列；ReentrantLock 等的地基
```
