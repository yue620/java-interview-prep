## 一、先建立直觉：HashMap 是什么

想象一个**储物柜大厅**：

- 大厅里有 16 个柜子（**数组**，下标 0~15）
- 你存东西时不自己选柜子，而是把"标签"（key）交给一台机器，机器根据标签算出柜号（**hash → 下标**）
- 万一两个人的标签算出了同一个柜号（**哈希冲突**），就在这个柜子门口拉一条**链子**，后来的挂在链子上（**链表**）
- 某个柜子的链子挂太多东西了（≥8 个），找起来慢，就换成一个**更高效的收纳架**（**红黑树**）

这就是 HashMap：**数组 + 链表 + 红黑树**。

```
数组 table（长度 16）
┌────┬────┬────┬────┬─────┐
│ 0  │ 1  │ 2  │... │ 15  │
└────┴────┴────┴────┴─────┘
        │
        ▼ 哈希冲突，挂链表
      Node → Node → Node
      （≥8 且容量 ≥64 时转红黑树）
```

## 二、put 一个键值对时，发生了什么

以 `map.put("张三", 90)` 为例，一步步走：

**第 1 步：算 hash 值**

```java
h = key.hashCode();      // 假设 "张三".hashCode() = 774889
hash = h ^ (h >>> 16);   // 扰动函数：高16位 与 低16位 异或
```

**第 2 步：算出放在哪个桶（数组下标）**

```java
index = (table.length - 1) & hash;   // 16 个桶就是 hash & 15
```

**第 3 步：看桶里有没有东西**

- 桶是空的 → 直接放新节点，完事
- 桶里有链表 → 顺着链表挨个比：
  - 找到**相同 key**（先比 hash，再用 `equals` 确认）→ 覆盖 value
  - 没找到 → 在链表末尾挂上新节点（JDK8 是**尾插法**）

**第 4 步：检查两件事**

- 这个桶的链表长度到 8 了吗？→ 且数组长度 ≥ 64 → 链表转红黑树
- 总元素个数超过 `容量 × 0.75` 了吗？→ 触发**扩容**

> 📌 记住这个流程，面试让你"描述 put 过程"就是考这四步。

## 三、三个"为什么"（面试必考的设计细节）

### 3.1 为什么容量必须是 2 的幂？

算下标用的是 `hash & (n - 1)`。

当 n = 16（二进制 10000）时，n - 1 = 15（二进制 **01111**），和任何 hash 做 `&` 运算，结果必然落在 0~15，**等价于取模 `hash % 16`，但位运算快得多**。

如果 n 不是 2 的幂，比如 n = 10，n - 1 = 9（二进制 01001），`&` 运算有些下标**永远算不出来**（比如 2、4），部分桶被浪费，冲突变多。

> 一句话答案：**2 的幂让 `&` 运算等价于取模，既快又能均匀分布。**

### 3.2 为什么要有扰动函数 `h ^ (h >>> 16)`？

想一下：如果容量只有 16，算下标时 `hash & 15` **只用了 hash 的低 4 位**，高位完全没参与。

两个不同的 key，如果低 4 位一样、高位不同，本来可以区分，现在直接冲突。

扰动函数把 hash 的**高 16 位右移下来，和低 16 位异或**，让高位信息混入低位 → 之后再取下标时，高位也参与了运算 → **冲突减少**。

> 一句话答案：**让 hash 的高位也参与下标计算，减少哈希冲突。**

### 3.3 为什么负载因子是 0.75？

负载因子 × 容量 = **扩容阈值**（16 × 0.75 = 12，存到第 13 个元素时扩容）。

- 太小（如 0.5）：空间浪费，数组很空就扩容
- 太大（如 1.0）：数组快满了才扩容，链表很长，查询变慢

0.75 是**空间和时间权衡后的经验值**（泊松分布统计下，0.75 时链表长度超过 8 的概率不到千万分之一——这也是树化阈值定为 8 的依据）。

## 四、扩容（resize）：HashMap 最重的操作

**触发条件**：`size > 容量 × 0.75`

**做什么**：新建一个**2 倍大小**的数组，把旧数组里所有节点**重新分配**到新数组。

### JDK8 的优化：高低位拆分（重要！）

旧容量 16 → 新容量 32。下标计算从 `hash & 15` 变成 `hash & 31`，区别只在**多看了一位**（第 5 位）。

所以每个节点在新数组里只有两种可能：

```
hash & 旧容量(16) == 0  →  留在原下标（比如还在 3 号桶）
hash & 旧容量(16) != 0  →  移到 原下标 + 旧容量（3 + 16 = 19 号桶）
```

**不用重新计算 hash，一次位运算就知道去哪**。这就是 `collection/ISSUE-001` 挑战任务 5 要你实现的东西。

### JDK7 的头插法死循环（JDK8 已修复，但面试常考）

JDK7 扩容时链表用**头插法**（新节点插到链表头部，节点顺序被反转），多线程并发扩容时两个线程互相反转对方已经处理过的节点，可能形成**环形链表** → 之后 `get` 时死循环，CPU 100%。

JDK8 改成**尾插法**保持顺序，解决了这个问题。但注意：**HashMap 在多线程下依然不安全**（会丢数据），只是不再死循环。

## 五、HashMap 线程不安全 → ConcurrentHashMap

### 5.1 HashMap 多线程下会出什么问题

两个线程同时 put 到同一个空桶：都判断"桶是空的"，都插入 → 后插入的把先插入的**覆盖掉，数据丢失**。

### 5.2 三个替代方案（从差到好）

| 方案 | 原理 | 问题 |
|---|---|---|
| `Hashtable` | 每个方法都加 `synchronized` | 锁整个表，并发度极低，已淘汰 |
| `Collections.synchronizedMap()` | 同上，锁整个 map | 同样锁太粗 |
| **`ConcurrentHashMap`** | 只锁冲突的那个桶 | ✅ 正确答案 |

### 5.3 ConcurrentHashMap 的两代实现

**JDK7：分段锁（Segment）**

把 16 个桶划分成若干"段"（默认 16 段），每段一把锁。线程操作不同段时互不阻塞 → 最多 16 个线程同时写。

**JDK8：CAS + synchronized（重点）**

- 桶是**空的** → 用 **CAS** 尝试插入新节点（无锁，快）
- 桶**已有节点** → 用 `synchronized` 锁住**这个桶的头节点**，再操作链表/红黑树

锁的粒度从"整张表"细化到"单个桶"，并发度大幅提升。

> 一句话答案：**JDK7 分段锁，JDK8 放弃分段改为 CAS + synchronized 锁桶头节点，粒度更细。**

## 六、ArrayList vs LinkedList（送分题，但要答全）

| | ArrayList | LinkedList |
|---|---|---|
| 底层 | 动态数组 | 双向链表 |
| 查（按下标） | **O(1)**，数组直接定位 | O(n)，从头遍历 |
| 头尾增删 | O(n)（扩容要拷贝数组） | **O(1)** |
| 内存 | 连续，可能有空闲容量 | 每个节点多存前后指针，更耗内存 |
| 扩容 | 默认 10，满了扩 **1.5 倍**，`Arrays.copyOf` 拷贝 | 无扩容概念 |

**实际开发几乎总选 ArrayList**——CPU 缓存对连续内存友好，即使中间插入，ArrayList 往往也比 LinkedList 快。LinkedList 只在"高频头尾操作"（如队列）时考虑。

## 七、equals 与 hashCode 的契约

HashMap 判断"两个 key 是否相同"靠两步：**hash 相同（定位到同一个桶）→ `equals` 返回 true（确认是同一个 key）**。

**约定**：如果 `a.equals(b)` 为 true，则 `a.hashCode()` 必须等于 `b.hashCode()`。

**违反会怎样**：你自定义一个类当 key，只重写 equals 不重写 hashCode → 两个"逻辑相等"的 key hashCode 不同 → 被分到不同桶 → `map.get()` 永远拿不到你刚 put 进去的值（拿到 null）。

> 所以：**重写 equals 必须同时重写 hashCode**。IDEA 可以一键生成（Alt + Insert）。
