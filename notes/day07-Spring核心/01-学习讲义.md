# Day 7 学习讲义（零基础版）：Spring 核心 —— IoC、Bean、AOP

> Spring 是 Java 后端面试的"主场"。零基础学法：每个概念都先想"没有 Spring 时你要自己干什么"。
> 老规矩：读一节 → 敲一节 → 跑一节。

---

## 〇、先搞懂：Spring 到底解决了什么

没有 Spring 时，你要自己 new 对象：

```java
// 没有 Spring 的世界
public class OrderService {
    private UserRepository repo = new UserRepository();      // 自己 new
    // UserRepository 里又 new 了 DataSource，DataSource 里又 new 了……
    // 改一个实现类，要改一串代码，测试也没法换假对象
}
```

有 Spring 后：**对象的创建、组装、销毁全交给一个叫"容器"的大管家**，你只管声明"我需要什么"。

```
你：我需要一个 UserRepository（声明依赖）
Spring 容器：给你，我早创建好了（注入）
```

这就是 **IoC（Inversion of Control，控制反转）**：创建对象的控制权，从你的代码"反转"给了容器。
**DI（Dependency Injection，依赖注入）** 是实现 IoC 的手段：容器把你需要的对象"注射"进来。

> 一句话记忆：**IoC 是思想（控制权交出去），DI 是做法（容器帮你注入）。**

## 一、IoC 容器与 Bean：被容器管理的对象

**Bean = 被 Spring 容器创建和管理的对象。** 你的类加个注解，就"登记"进了容器：

```java
@Component   // 告诉 Spring：帮我管理这个类 → 它就变成了一个 Bean
public class UserRepository { }

@Service     // 业务层专用（功能同 @Component，语义更清晰）
public class UserService {
    private final UserRepository repo;

    // 构造方法注入（推荐写法）：Spring 看到构造方法，自动把容器里的 UserRepository 传进来
    public UserService(UserRepository repo) {
        this.repo = repo;
    }
}
```

常用登记注解（效果一样，按层区分语义）：

| 注解 | 用在哪 |
|---|---|
| `@Component` | 通用 |
| `@Service` | 业务层 |
| `@Repository` | 数据访问层 |
| `@Controller` / `@RestController` | Web 层 |

注入方式三种，**面试只推荐构造方法注入**：

```java
// ① 字段注入（不推荐：隐藏依赖、没法 final、测试难）
@Autowired
private UserRepository repo;

// ② setter 注入（可选依赖才用）
@Autowired
public void setRepo(UserRepository repo) { this.repo = repo; }

// ③ 构造方法注入（推荐：依赖一目了然、可以 final、强制必填）
public UserService(UserRepository repo) { this.repo = repo; }
```

### 动手感受 IoC（在 mini-mall 里跑）

```java
@SpringBootApplication
public class MallApplication {
    public static void main(String[] args) {
        // 启动后返回的"容器"本身，可以从中取 Bean
        var ctx = SpringApplication.run(MallApplication.class, args);
        UserService s1 = ctx.getBean(UserService.class);
        UserService s2 = ctx.getBean(UserService.class);
        System.out.println(s1 == s2);  // true —— 默认单例！容器里只有一个
    }
}
```

## 二、Bean 的作用域：容器给你"一个"还是"每次一个新的"

| 作用域 | 含义 | 使用场景 |
|---|---|---|
| **singleton（默认）** | 整个容器只有一个实例 | 99% 的情况（Service/Repository 无状态，安全） |
| prototype | 每次 getBean 都 new 一个新的 | 有状态的对象（很少用） |
| request / session | Web 中每个 HTTP 请求/会话一个 | 存放请求级数据 |

> 面试追问：**单例 Bean 线程安全吗？**
> 答：Bean 本身不保证。无状态（没有可变成员变量）的 Service 是安全的；如果你在单例 Bean 里放了可变成员变量（如 `private int count`），多线程并发改就会出错。解法：成员变量用 ThreadLocal，或改成局部变量。

## 三、Bean 的生命周期：从 new 到销毁的全过程 ⭐高频

面试题："说说 Bean 的生命周期"。记住这条流水线：

```
1. 实例化（new 出对象，此时字段都是 null）
2. 属性填充（依赖注入，把 @Autowired 的字段填上）
3. Aware 回调（BeanNameAware 等，让 Bean 知道自己的名字/容器）
4. BeanPostProcessor【前置】处理  ← AOP 代理就在这一步之后生成
5. 初始化：@PostConstruct 方法 → InitializingBean.afterPropertiesSet() → 自定义 init-method
6. BeanPostProcessor【后置】处理  ← AOP 代理实际在这里返回代理对象
7. Bean 就绪，可以使用
8. 容器关闭时销毁：@PreDestroy → DisposableBean.destroy() → 自定义 destroy-method
```

### 亲手看见生命周期（可运行示例）

```java
@Component
public class LifeBean {
    public LifeBean() {
        System.out.println("1. 构造方法：对象被 new 出来了");
    }

    @PostConstruct
    public void init() {
        System.out.println("2. @PostConstruct：依赖注入完毕，初始化");
    }

    @PreDestroy
    public void close() {
        System.out.println("3. @PreDestroy：容器关闭，我要销毁了");
    }
}
```

启动 Spring Boot 看控制台，顺序永远是 1 → 2；`Ctrl+C` 或调用 `ctx.close()` 时打印 3。

> 采分点：能说出"实例化 → 属性填充 → 初始化（@PostConstruct）→ 使用中 → 销毁（@PreDestroy）"主线 + 提到 **BeanPostProcessor**（AOP 代理生成的位置）就是高分答案。

## 四、循环依赖：A 要 B，B 要 A ⭐高频

```java
@Service
public class AService {
    private final BService b;   // A 依赖 B
    public AService(BService b) { this.b = b; }
}

@Service
public class BService {
    private final AService a;   // B 又依赖 A → 死循环！
    public BService(AService a) { this.a = a; }
}
```

**Spring 怎么解决？三级缓存**（本质是三个 Map）：

```
一级缓存 singletonObjects     ：成品 Bean（初始化完的）
二级缓存 earlySingletonObjects：半成品 Bean（new 了但没注入完）
三级缓存 singletonFactories   ：对象工厂（能生产"早期引用"，支持 AOP 代理）
```

流程（以 A、B 循环依赖为例）：

1. 创建 A：先 new 出 A 的裸对象 → 把"A 的工厂"放进**三级缓存**
2. A 填充属性时发现需要 B → 去创建 B
3. B 填充属性时发现需要 A → 从**三级缓存**拿到 A 的早期引用（裸对象，可能包成代理）→ 放进**二级缓存**
4. B 完成创建 → 放进**一级缓存**
5. 回到 A，注入完整的 B → A 完成创建

> 关键记忆：**构造方法循环依赖无解**（new A 需要 B，new B 需要 A，连裸对象都造不出来，启动直接报错 `BeanCurrentlyInCreationException`）。Spring 只能解决 **setter/字段注入** 的单例循环依赖。
> 所以"推荐构造方法注入"的另一个理由就是：**让循环依赖在启动时直接暴露，而不是被缓存悄悄掩盖设计问题。**

## 五、AOP：不改业务代码，给它"套一层"统一功能 ⭐高频

场景：你想给所有 Service 方法记录耗时。笨办法是每个方法里写 `start/stop` 计时 —— 业务代码被污染。AOP 的做法：

```java
@Aspect          // 声明：这是一个"切面"，装着要横切进去的逻辑
@Component
public class TimeAspect {

    // 切点：拦截 service 包下所有类的所有方法
    @Around("execution(* com.example.mall.service.*.*(..))")
    public Object around(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.currentTimeMillis();
        Object result = pjp.proceed();              // ← 真正执行原方法
        System.out.println(pjp.getSignature() + " 耗时 "
                + (System.currentTimeMillis() - start) + "ms");
        return result;
    }
}
```

核心词汇表（面试必背）：

| 术语 | 人话 |
|---|---|
| 切面 Aspect | 装横切逻辑的类（上面的 TimeAspect） |
| 切点 Pointcut | "在哪里切" —— 匹配哪些方法 |
| 通知 Advice | "切进去干什么" —— @Before/@After/@Around/@AfterReturning/@AfterThrowing |
| 连接点 JoinPoint | 被拦截到的那次方法调用 |

### AOP 底层：动态代理

你拿到的 Service Bean **不是你写的类本身，而是 Spring 生成的代理对象**，方法调用先经过代理，代理里织入通知逻辑再调原方法。

两种代理方式：

| | JDK 动态代理 | CGLIB 代理 |
|---|---|---|
| 原理 | 反射，运行时生成**接口**的实现类 | 字节码增强，生成目标类的**子类** |
| 前提 | 目标必须实现接口 | 不需要接口，但不能代理 final 类/方法 |
| Spring Boot 2.x+ 默认 | | ✅ 默认用 CGLIB |

> 这就是为什么 **@Transactional 自调用会失效**（Day 8 详解）：`this.foo()` 走的是"对象自己的方法"，没经过代理，增强逻辑（事务）根本没机会执行。AOP 代理是理解 Spring 事务失效的钥匙。
