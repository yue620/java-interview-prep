# Day 6 自测清单 · 参考答案

> ⚠️ 先口述，再对照。答案只列采分点。

---

**1. JVM 内存区域**

五个：堆（对象实例，共享）、虚拟机栈（方法栈帧/局部变量，私有）、方法区（类信息/静态变量/常量，共享）、程序计数器（当前行号，私有，唯一不 OOM）、本地方法栈（native 方法，私有）。

**2. OOM vs StackOverflowError**

OOM 发生在堆（对象塞满，如无限 add 进 List）或方法区；StackOverflowError 发生在虚拟机栈——方法调用太深（典型：递归没写终止条件），每次调用压一个栈帧，栈深有限被撑爆。

**3. 堆的分代**

新生代（Eden + 两个 Survivor，默认 8:1:1）和老年代。分代原因：98% 对象朝生夕死，新生代用复制算法快速收短命对象，老年代存熬过多次 GC 的长寿对象，用标记整理。新对象进 Eden，熬过一次 Minor GC 进 Survivor，熬够次数晋升老年代。

**4. 可达性分析**

从 GC Roots 出发向下搜索，引用链上走得到的对象是活的，走不到的是垃圾（可回收）。不用引用计数的原因：解决不了循环引用（A 引用 B、B 引用 A，无外部引用但计数不为 0，永远回收不了）。

**5. GC Roots 有哪些**

虚拟机栈里的局部变量引用的对象、方法区的 static 变量引用的对象、常量引用的对象、JNI（本地方法）引用的对象。

**6. 三种 GC 算法**

标记-清除：标记后删除，简单但有内存碎片；复制：活对象复制到另一半、旧半整体清空，快且无碎片但浪费一半空间（新生代用，Eden+Survivor 配合）；标记-整理：活对象向一端移动排齐，无碎片但移动慢（老年代用）。

**7. Minor GC vs Full GC / STW**

Minor GC 只清新生代，Eden 满时触发，频繁但快；Full GC 清整个堆（新生代+老年代+方法区），慢且 STW 长。STW = Stop The World，GC 时暂停所有用户线程。调优目标之一就是减少 Full GC 次数和停顿。

**8. CMS vs G1**

CMS：老年代收集器，主打低停顿，大部分回收工作与用户线程并发执行；G1（JDK9+ 默认）：把堆划分为多个 Region，可预测停顿（指定最大停顿时间，它自己安排回收哪些 Region）。

**9. 类加载五过程 + 准备 vs 初始化**

加载（读字节流生成 Class 对象）→ 验证（字节码合法安全）→ 准备（给 static 变量分配内存设默认值，int 为 0）→ 解析（符号引用转直接引用）→ 初始化（执行 static 赋值和 static 块，真正赋值）。
陷阱：`static int a = 5;` 准备阶段 a=0，初始化阶段才 a=5。

**10. 双亲委派**

类加载器收到加载请求，先委托父加载器，父不行才自己加载。好处：① 避免重复加载（全程序一份）；② 安全——伪造的 java.lang.String 会被一路委派到启动类加载器，加载的是正牌核心类，伪造类没机会生效。

**11. 三层类加载器**

启动类加载器（Bootstrap，C++ 实现）：加载 JAVA_HOME/lib 核心类（String 等）；扩展/平台类加载器：加载扩展目录；应用类加载器（AppClassLoader）：加载自己写的类。String.class.getClassLoader() 返回 null 是因为 Bootstrap 由 C++ 实现，Java 层拿不到引用，约定用 null 表示。
