## 〇、先搞懂：JVM 在管什么

你写的 `new Object()`，对象放哪？方法执行时局部变量放哪？不再用的对象谁清理？类从 .class 文件怎么变成能跑的程序？——这些全是 JVM 在管。JVM 八股就是三大块：**内存怎么分（区域）、垃圾怎么收（GC）、类怎么进来（类加载）**。

## 一、JVM 内存区域：五个"房间"

程序跑起来后，JVM 把内存划成五个区域。**面试第一问就是"JVM 内存分为哪几块"**：

```
┌─────────────────── JVM 运行时内存 ───────────────────┐
│  所有线程共享                    │  每个线程私有        │
│  ┌─────────────┐ ┌───────────┐ │ ┌──────┐ ┌───────┐ │
│  │     堆       │ │  方法区    │ │ │虚拟机栈│ │程序计数器│ │
│  │ (对象都在这) │ │(类信息/常量)│ │ │(方法调用)│ │(行号指示)│ │
│  └─────────────┘ └───────────┘ │ └──────┘ └───────┘ │
│                                 │ + 本地方法栈        │
└─────────────────────────────────┴────────────────────┘
```

### 逐个房间看（带代码对照）

```java
public class RoomDemo {                    // 类信息 → 方法区
    static int CLASS_VAR = 1;              // 静态变量 → 方法区

    public static void main(String[] args) {
        int local = 10;                    // 局部变量 → 虚拟机栈（main 的栈帧里）
        Object obj = new Object();         // 对象本体 → 堆；obj 引用 → 栈
    }
}
```

| 区域 | 存什么 | 会出什么错（必考） | 线程 |
|---|---|---|---|
| **堆** | 几乎所有对象实例 | **OutOfMemoryError**（OOM） | 共享 |
| **虚拟机栈** | 方法调用的栈帧（局部变量、返回地址） | **StackOverflowError**（递归太深） | 私有 |
| **方法区** | 类信息、静态变量、常量 | OOM（Metaspace） | 共享 |
| **程序计数器** | 当前线程执行到哪一行 | **唯一不会 OOM 的区域** | 私有 |
| 本地方法栈 | native 方法 | StackOverflow | 私有 |

**两个必考错误先记住**（示例 1、2 会亲手制造）：

- 堆满了 → `OutOfMemoryError: Java heap space`
- 递归没写终止条件 → `StackOverflowError`（每次方法调用往栈里压一个栈帧，栈深有限）

### 堆的内部：为什么要分代（GC 的伏笔）

```
堆
├── 新生代（新对象都生在这）
│   ├── Eden 区（8 份）        ← new 出来的对象先进 Eden
│   └── Survivor 区（1+1 份）   ← 熬过 GC 的幸存者在这俩区之间倒腾
└── 老年代                      ← 熬过很多次 GC 还活着的"老不死"搬来这
```

**为什么分代**：统计发现**98% 的对象朝生夕死**（比如方法里的临时对象）。所以新生代用"复制算法"快速回收短命对象，老年代用"标记整理"对付长寿对象——不同区域用不同算法，效率最高。

## 二、垃圾回收（GC）：怎么判断、怎么收

### 2.1 第一步：判断谁是垃圾——可达性分析

**问题**：JDK 判断对象死活不用"引用计数"（数有几个人引用你），因为解决不了**循环引用**（A 引用 B、B 引用 A，都没人用了但计数不为 0）。

**正解：可达性分析**——从一批"根"（GC Roots）出发往下找，**走不到的对象就是垃圾**：

```
GC Roots（根：栈里的局部变量、static 变量、常量、JNI 引用）
   │
   ▼
对象 A ──引用──→ 对象 B ──引用──→ 对象 C     ✅ 可达，活着
                                         
对象 D ←──引用──→ 对象 E   （D、E 互相引用，但从 Roots 走不到）
                 ↑ 都是垃圾，回收 ✅（引用计数法在这里会误判）
```

**示例 1：亲手制造 OOM（堆满）**

```java
import java.util.ArrayList;
import java.util.List;

public class OomDemo {
    public static void main(String[] args) {
        List<byte[]> list = new ArrayList<>();   // list 拽着所有对象 → 全都可达 → 都不是垃圾
        while (true) {
            list.add(new byte[1024 * 1024]);     // 每次 new 1MB，无限塞
            System.out.println("已分配 " + list.size() + " MB");
        }
    }
}
```

> ⚠️ 运行时把堆调小效果更明显：IDEA 的 Run Configuration → VM options 加 `-Xmx20m`（最大堆 20MB）。几秒后就会看到：
> `Exception in thread "main" java.lang.OutOfMemoryError: Java heap space`
> 这就是明天实验的主角，先混个脸熟。

### 2.2 第二步：怎么收——三种基础算法

| 算法 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **标记-清除** | 标记垃圾 → 直接删 | 简单 | 留下**内存碎片** |
| **复制**（新生代用） | 活着的复制到另一半内存，旧的一半整体清空 | 快、无碎片 | 浪费一半内存 |
| **标记-整理**（老年代用） | 标记后把活的**挪到一边排整齐** | 无碎片不浪费 | 移动对象，慢 |

**新生代的复制算法细节**（Eden + 两个 Survivor）：GC 时把 Eden 和 Survivor-from 里活着的复制到 Survivor-to，然后清空 Eden 和 from——因为 98% 都是垃圾，要复制的活对象很少，所以快。

### 2.3 Minor GC vs Full GC（高频）

| | Minor GC | Full GC |
|---|---|---|
| 收拾谁 | 只清**新生代** | **整个堆**（新生代+老年代+方法区） |
| 触发 | Eden 满了 | 老年代满了等 |
| 速度 | 快（对象大多短命） | **慢得多**，STW 时间长 |
| STW | Stop The World：GC 时暂停所有用户线程，Full GC 的 STW 是性能杀手 | |

**面试一句**：Minor GC 频繁但快，Full GC 少但慢且 STW 长——调优的目标之一就是减少 Full GC。

### 2.4 垃圾收集器（知道名字和特点即可）

| 收集器 | 特点 |
|---|---|
| Serial / Parallel | 老款，单线程 / 多线程并行 |
| **CMS** | 老年代收集器，主打**低停顿**，大部分工作和用户线程并发 |
| **G1**（JDK9+ 默认） | 把堆切成很多 Region，**可预测停顿**（告诉它"最多停 200ms"，它自己安排） |

## 三、类加载：.class 文件怎么变成能跑的程序

### 3.1 过程五步（能按顺序说出来）

```
加载 → 验证 → 准备 → 解析 → 初始化
```

| 阶段 | 干什么 | 一句话记忆 |
|---|---|---|
| 加载 | 读 .class 字节流，生成 Class 对象 | 把文件读进来 |
| 验证 | 检查字节码安不安全、合不合法 | 安检 |
| 准备 | 给 **static 变量分配内存并设默认值**（int=0） | 分地皮 |
| 解析 | 符号引用 → 直接引用 | 对号入座 |
| 初始化 | 执行 static 赋值和 static 块（**真正赋值**） | 精装修 |

> 注意区分"准备"和"初始化"：`static int a = 5;` 在**准备**阶段 a=0（默认值），到**初始化**阶段才 a=5。这是高频陷阱。

### 3.2 类加载器与双亲委派（必考）

**三层类加载器**：

```
启动类加载器（Bootstrap）     ← 加载 JAVA_HOME/lib 核心类（String 等）
      ↑ 父亲
扩展类加载器（Extension）     ← 加载扩展目录
      ↑ 父亲
应用类加载器（AppClassLoader） ← 加载你自己写的类
      ↑ 父亲
自定义类加载器
```

**双亲委派机制**：一个类加载器收到加载请求时，**先问父亲"你加载过吗/你能加载吗"，父亲不行才自己来**。

**为什么这样设计（两个好处）**：
1. **避免重复加载**：父亲加载过的类，孩子不再加载，全程序只有一份
2. **安全**：你自己写一个 `java.lang.String` 想偷梁换柱？双亲委派会一路委托给启动类加载器，它加载的是**正牌** String，你的假冒货根本没机会被加载。

**示例 2：看一眼类加载器的家谱**

```java
public class ClassLoaderDemo {
    public static void main(String[] args) {
        ClassLoader cl = ClassLoaderDemo.class.getClassLoader();
        System.out.println("我的类加载器: " + cl);           // AppClassLoader
        System.out.println("它的父亲:   " + cl.getParent()); // PlatformClassLoader(JDK9+)
        System.out.println("父亲的父亲: " + cl.getParent().getParent()); // null（Bootstrap 是 C++ 写的，Java 里拿不到，显示 null）

        System.out.println("String 的类加载器: " + String.class.getClassLoader()); // null → Bootstrap
    }
}
```

> `null` 不代表没有——Bootstrap 是 C++ 实现的，Java 层面拿不到引用，所以打印 null。

## 四、本日知识地图

```
JVM 内存五区域
├── 堆（共享）：对象实例 → OOM；内部分新生代(Eden+2×Survivor)/老年代
├── 虚拟机栈（私有）：方法栈帧/局部变量 → StackOverflowError
├── 方法区（共享）：类信息/静态变量/常量
├── 程序计数器（私有）：行号，唯一不会 OOM
└── 本地方法栈：native 方法

GC
├── 判断垃圾：可达性分析（GC Roots 出发，走不到即死）；引用计数败给循环引用
├── 算法：标记清除(碎片) / 复制(新生代) / 标记整理(老年代)
├── Minor GC(新生代，快) vs Full GC(全堆，慢，STW 长)
└── 收集器：CMS 低停顿、G1 可预测停顿(JDK9+默认)

类加载
├── 五步：加载→验证→准备(static 默认值)→解析→初始化(static 真正赋值)
├── 三层加载器：Bootstrap → Extension → App
└── 双亲委派：先问父亲 → 防重复加载 + 防伪造核心类（安全）
```
