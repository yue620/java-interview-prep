# Day 11 学习讲义（零基础版）：Redis

> Redis 篇的学法：把它想成"一个超快的、住在内存里的 Map"。所有八股都围绕：数据怎么存（类型）、断电怎么办（持久化）、缓存出问题怎么办（三大经典问题）、多实例抢资源怎么办（分布式锁）。
> 实践：mini-mall 商品缓存 + 穿透复现修复 + 分布式锁防超卖（ISSUE-010）。

## 〇、先搞懂：为什么需要 Redis

```
浏览器 → Java 服务 → MySQL（磁盘，一次查询几毫秒）
```

- MySQL 数据在磁盘，扛不住每秒几万次查询
- Redis 数据在**内存**，一次操作**微秒级**，单机 QPS 可达 10 万
- 经典架构：**先查 Redis，没有再查 MySQL，查到后写回 Redis**（叫 Cache Aside，下面详讲）

```java
// 伪代码：缓存使用三板斧
String json = redis.get("product:" + id);     // 1. 先查缓存
if (json != null) return parse(json);          // 2. 命中直接返回
Product p = productMapper.selectById(id);      // 3. 没命中查数据库
redis.set("product:" + id, toJson(p), 300s);   // 4. 写回缓存，设过期时间
return p;
```

## 一、五大基本类型 ⭐必考

| 类型 | 底层（能答加分） | 典型用途 |
|---|---|---|
| **String** | SDS 简单动态字符串 | 缓存对象（JSON）、计数器（INCR）、分布式锁 |
| **Hash** | ziplist/listpack + hashtable | 存对象字段（用户资料），可单独改一个字段 |
| **List** | quicklist | 消息队列（LPUSH+BRPOP）、最新列表 |
| **Set** | intset + hashtable | 去重、共同好友（交集 SINTER）、抽奖 |
| **ZSet（有序集合）** | listpack + **跳表** | **排行榜**（分数排序）、延迟队列 |

```bash
# 快速感受（在 redis-cli 里敲）
SET product:1 '{"name":"iPhone","price":5999}'
GET product:1
HSET user:1 name "张三" age 20
ZADD rank 100 "玩家A" && ZADD rank 200 "玩家B" && ZREVRANGE rank 0 -1 WITHSCORES
```

> 追问跳表（ZSet 底层）：**多层有序链表，上层是下层的"快车道"索引**，查找 O(log n)，比红黑树实现简单、范围查询更方便。

## 二、持久化：内存断电就没了，怎么办 ⭐高频

| | RDB（快照） | AOF（追加日志） |
|---|---|---|
| 原理 | 定时把**整个内存拍快照**存 dump.rdb | 把**每条写命令追加**到日志文件 |
| 恢复速度 | 快（直接加载数据） | 慢（要重放命令） |
| 数据丢失 | 可能丢**最后一次快照之后**的数据 | 最多丢 1 秒（everysec 策略） |
| 文件大小 | 小（二进制压缩） | 大（可通过 rewrite 压缩） |
| 类比 | 游戏存档 | 操作录像 |

> 标准答案：**生产环境 RDB + AOF 混合用**。Redis 4.0+ 支持混合持久化：AOF 文件前半段是 RDB 快照、后半段是增量命令，恢复又快又全。

## 三、缓存三大经典问题 ⭐⭐必考

### ① 缓存穿透：查"根本不存在"的数据

```
恶意请求：GET /product/-1（数据库也没有）
→ 缓存永远没有 → 每次请求都打穿到数据库 → 数据库被压垮
```

**解法**：
- **缓存空对象**：数据库查不到也缓存 `null`（短过期时间，如 30 秒）—— 简单，首选
- **布隆过滤器**：一个超省内存的位图，快速判断"这个 key 一定不存在/可能存在"，把不存在的请求直接拦在 Redis 前面

### ② 缓存击穿：一个**热点 key** 刚好过期

```
爆款商品 key 过期的那一瞬间，1 万个请求同时发现缓存没有
→ 1 万个请求同时去查数据库重建缓存 → 数据库瞬间被打爆
```

**解法**：
- **互斥锁（逻辑单线程重建）**：第一个发现缓存失效的线程抢锁，**只有一个线程去查库重建**，其他线程等待后读新缓存（实践里亲手实现）
- **逻辑过期**：key 不设物理过期，value 里存逻辑过期时间，过期了异步开线程更新，先返回旧数据

### ③ 缓存雪崩：**大量 key 同时**过期 / Redis 宕机

```
所有缓存在同一时刻集体过期 → 全部请求涌向数据库
```

**解法**：
- **过期时间加随机值**：`300 + random(60)` 秒，错开过期时刻
- Redis 高可用：主从 + 哨兵/集群
- 兜底：熔断降级、限流

> 区分口诀：**穿透 = 查不存在的；击穿 = 一个热点的过期了；雪崩 = 一大片同时过期。**

## 四、缓存与数据库一致性：Cache Aside 模式 ⭐高频

更新数据时，缓存怎么办？标准答案 **Cache Aside（旁路缓存）**：

```
读：先读缓存 → 没有读数据库 → 写回缓存
写：先更新数据库 → 再【删除】缓存（不是更新缓存！）
```

经典追问 1：**为什么是"删除缓存"而不是"更新缓存"？**
- 如果缓存的值要经过复杂计算，每次写都更新太浪费
- 更新缓存有并发问题：两个写线程顺序错乱会把旧值写回缓存

经典追问 2：**先删缓存还是先更新数据库？**
- 推荐**先更新数据库，再删缓存**。反过来有窗口：删完缓存还没更新库，另一个线程读到旧值写回缓存
- 还要更强一致 → **延迟双删**（删缓存 → 更新库 → 延时再删一次）或订阅 binlog（Canal）

## 五、分布式锁：多台机器抢一把锁 ⭐⭐必考（实践核心）

单机 `synchronized` 只能锁**一个 JVM**。服务部署多台机器后，必须用 Redis 做跨机器的锁。

### 版本 1：SET NX PX（核心命令）

```bash
SET lock:product:1 "uuid-xxx" NX PX 30000
# NX：key 不存在才能设置成功（= 抢到锁），存在则失败
# PX 30000：30 秒自动过期（防止持锁机器宕机导致死锁）
```

**为什么必须一条命令完成**：如果分成 `SETNX` + `EXPIRE` 两条，第一条执行完机器宕机，锁永远不释放 → 死锁。原子性！

### 版本 2：解锁的坑 —— 别删了别人的锁

```
A 抢到锁，业务执行 35 秒（超过 30s 过期时间）
→ 锁自动过期，B 抢到锁
→ A 执行完，DEL 把 B 的锁删了！
```

**解法**：value 存唯一标识（UUID），解锁时**先比对是不是自己的锁再删**（比对+删除要用 Lua 脚本保证原子性）：

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

### 版本 3：Redisson（生产正解）

上面还有个问题：业务没执行完锁就过期了怎么办？**Redisson 的看门狗（watchdog）**：默认锁 30 秒，后台线程每 10 秒检查一次，只要你还持有锁就自动续期。

> 面试话术："简单场景用 SET NX PX + Lua 解锁就够了；生产上推荐 Redisson，它解决了**自动续期（看门狗）**、**可重入**、**锁等待**这些问题。"

## 六、Redis 其他速记点（抽查可能问）

- **为什么快**：纯内存 + 单线程处理命令（无锁竞争、无上下文切换）+ IO 多路复用 + 高效数据结构。追问："单线程为什么还快？"——内存操作瓶颈不在 CPU
- **过期删除策略**：**惰性删除**（用到时才检查过期）+ **定期删除**（后台抽样清理）
- **内存淘汰策略**：内存满了怎么办？`allkeys-lru`（淘汰最近最少使用的，缓存场景推荐）
