# Day 9 学习讲义（零基础版）：MySQL 索引

> MySQL 篇的学法：所有概念都用"查字典"来类比。索引 = 字典的部首目录。
> 实践：mini-mall 造 10w 数据，慢查询加索引，explain 前后对比（ISSUE-008）。

---

## 〇、先搞懂：没有索引会怎样

```sql
SELECT * FROM product WHERE name = 'iPhone';
```

没有索引：MySQL 把表里**每一行都读出来**比对（全表扫描）。10 万行就读 10 万次磁盘。
有索引：像查字典先翻部首目录，**几次磁盘 IO 就定位到那一行**。

索引的本质：**一种排好序的数据结构（B+ 树），用额外的存储空间换查询速度。**

---

## 一、为什么索引用 B+ 树 ⭐必考

候选数据结构逐个淘汰（面试喜欢这样追问）：

| 结构 | 为什么不行 |
|---|---|
| 哈希表 | 等值查询 O(1) 很快，但**不支持范围查询**（`WHERE age > 18` 抓瞎）、不支持排序 |
| 二叉查找树 | 数据量大时**树太高**，可能退化成链表 |
| 红黑树 | 树还是太高。树高 = 磁盘 IO 次数，1 亿行树高 20+ 层，要命 |
| B 树 | 每个节点都存数据，**非叶子节点能存的索引少**，树还是偏高 |
| **B+ 树** ✅ | **只有叶子节点存数据**，非叶子节点只存索引 → 一个节点存上千个索引 → **3~4 层就能装下千万级数据**；**叶子节点用链表串起来** → 范围查询顺着链表扫，飞快 |

```
B+ 树长相（树很矮，叶子相连）：
              [ 10 | 20 | 30 ]          ← 非叶子：只存索引，矮胖
             /     |    |     \
        [1..9] [10..19][20..29][30..]    ← 叶子：存数据，互相用链表连 →
```

> 一句话答案：**B+ 树矮胖（减少磁盘 IO）+ 叶子链表相连（范围查询快）。**

## 二、聚簇索引 vs 非聚簇索引（回表）⭐必考

InnoDB 里主键索引就是**聚簇索引**：

- **聚簇索引（主键索引）**：叶子节点存的是**整行数据**。一张表只有一个
- **非聚簇索引（二级索引/普通索引）**：叶子节点存的是**索引列的值 + 主键值**

关键推论 —— **回表**：

```sql
-- name 上有普通索引
SELECT * FROM product WHERE name = 'iPhone';
-- 执行过程：
-- 1. 走 name 索引的 B+ 树，找到叶子：name='iPhone', id=1001
-- 2. 但 SELECT * 要整行数据，索引里没有
-- 3. 拿着 id=1001 再去主键索引里查一次 ← 多查一棵树，这一步叫"回表"
```

**覆盖索引**（回表的反面，优化神器）：

```sql
SELECT id, name FROM product WHERE name = 'iPhone';
-- 要的列（id, name）在索引叶子里全有 → 不用回表，叫覆盖索引
-- explain 的 Extra 列会显示 Using index
```

## 三、联合索引与最左前缀原则 ⭐必考

联合索引 `(a, b, c)` 相当于建了一棵按 **a 排序、a 相同按 b 排序、b 相同按 c 排序** 的 B+ 树。

**最左前缀：查询必须从索引的最左列开始用，才能命中；跳过中间列，后面的列失效。**

```sql
-- 有联合索引 (name, price, stock)

SELECT * FROM product WHERE name = 'A' AND price = 100 AND stock > 0;  -- ✅ 三列全用上
SELECT * FROM product WHERE name = 'A' AND price = 100;                -- ✅ 用上前两列
SELECT * FROM product WHERE name = 'A';                                -- ✅ 用上第一列
SELECT * FROM product WHERE price = 100;                               -- ❌ 跳过 name，索引失效
SELECT * FROM product WHERE name = 'A' AND stock > 0;                  -- ⚠️ 只用上 name，stock 用不上
```

> 类比：查字典按"拼音+笔画"排序。你知道拼音才能用笔画继续查；直接给笔画没法查。

## 四、索引失效场景清单 ⭐高频

```sql
-- ① 对索引列使用函数或运算
WHERE DATE(create_time) = '2026-08-01'   -- ❌ 改成范围：create_time >= ... AND create_time < ...
WHERE price + 10 = 100                    -- ❌ 改成 price = 90

-- ② 隐式类型转换（phone 是 varchar，传了数字）
WHERE phone = 13800138000                 -- ❌ 加引号 '13800138000'

-- ③ like 以 % 开头
WHERE name LIKE '%手机'                    -- ❌ 最左字符不确定，没法用树
WHERE name LIKE '手机%'                    -- ✅ 可以

-- ④ 违反最左前缀（见上节）

-- ⑤ or 连接的条件里有列没索引
WHERE name = 'A' OR description = 'B'     -- description 没索引 → 全失效

-- ⑥ MySQL 优化器判断"全表扫描更快"（如数据量太小、索引区分度太低）
```

## 五、explain：看 MySQL 打算怎么执行你的 SQL ⭐必考（实践核心）

```sql
EXPLAIN SELECT * FROM product WHERE name = 'iPhone';
```

重点看这几列：

| 列 | 看什么 |
|---|---|
| **type** | 访问类型，从好到坏：`const > eq_ref > ref > range > index > ALL`。**出现 ALL（全表扫描）就要优化** |
| **key** | 实际用了哪个索引。NULL = 没用索引 |
| **rows** | 预计扫描行数，越小越好 |
| **Extra** | `Using index`（覆盖索引，好）；`Using filesort`（额外排序，差）；`Using temporary`（临时表，差） |

### 动手实验（ISSUE-008 里做）

```sql
-- 加索引前
EXPLAIN SELECT * FROM product WHERE name = '商品99999';
-- type=ALL, rows=100000, key=NULL   ← 全表扫 10 万行

ALTER TABLE product ADD INDEX idx_name(name);

-- 加索引后
EXPLAIN SELECT * FROM product WHERE name = '商品99999';
-- type=ref, rows=1, key=idx_name    ← 只扫 1 行！
```

## 六、索引设计原则（实战话术）

1. **高频查询的 WHERE / ORDER BY / JOIN 列**建索引
2. **区分度高的列**优先（性别只有男女，区分度低，不值得建）
3. 联合索引按**最左前缀**设计，把等值查询的列放前面
4. 索引不是越多越好：**占空间 + 拖慢写操作**（insert/update 要维护索引树）
5. 能用**覆盖索引**就别回表
