# Day 9 自测清单答案（采分点版）

**1. 索引是什么 / 代价**
- **排好序的数据结构（B+ 树）**，用空间换时间，把 O(n) 全表扫描变成 O(log n) 树查找
- 代价：**占额外磁盘空间**；**拖慢写操作**（增删改要维护索引树）

**2. 为什么不用哈希表**
- 哈希只支持**等值查询**；**不支持范围查询**（>、<、BETWEEN）、**不支持排序**、模糊查询也不行；还有哈希冲突问题

**3. 为什么 B+ 树优于 B 树/红黑树**
- 数据库索引存在磁盘上，**树高 = 磁盘 IO 次数**，必须矮胖
- B+ 树**非叶子节点只存索引不存数据** → 单节点能存上千个索引项 → **3~4 层装下千万级数据**
- 红黑树是二叉树，数据量大树高几十层，IO 太多
- B 树非叶子也存数据，同样空间存索引少，树更高；且范围查询不如 B+ 树

**4. 叶子节点结构 + 范围查询**
- 叶子节点之间用**双向链表**相连；范围查询定位起点后**顺着链表顺序扫**即可，不用回到树顶重新查

**5. 聚簇/非聚簇 + 回表**
- 聚簇索引（InnoDB 主键索引）：叶子存**整行数据**，一表一个
- 非聚簇索引：叶子存**索引列值 + 主键值**
- 回表：二级索引查到主键后，**再查一次主键索引取整行**，多走一棵树

**6. 覆盖索引**
- 查询需要的列**全部包含在索引里**，无需回表
- 判断：explain 的 **Extra 显示 Using index**

**7. 联合索引命中判断**
- `where a=1` ✅ 命中 a
- `where b=1` ❌ 跳过最左列，失效
- `where a=1 and c=1` ⚠️ 只命中 a，c 用不上（b 断了）
- `where a=1 and b=1 order by c` ✅ 三列都受益，c 还能用上索引排序（避免 filesort）

**8. 索引失效场景（任 4）**
- 索引列上**用函数/运算**（`DATE(col)=`、`col+1=`）
- **隐式类型转换**（varchar 列传数字）
- **like '%xx'** 前缀通配
- **违反最左前缀**
- **or 两侧有列无索引**
- 优化器判断全表更快（数据少/区分度低）

**9. explain 关注列**
- **type**（`ALL` = 全表扫描要优化，目标至少 range/ref 级别）、**key**（NULL 即没用索引）、**rows**（扫描行数）、**Extra**（Using filesort / Using temporary 是坏信号，Using index 是好信号）

**10. 慢 SQL 排查思路（满分框架）**
- ① 开慢查询日志 / 用 explain 看执行计划
- ② 看 type 是否 ALL、key 是否命中索引、rows 量级
- ③ 没索引 → 按最左前缀建联合索引，尽量做成覆盖索引
- ④ 有索引没命中 → 排查失效场景（函数、隐式转换、like%、or）
- ⑤ 索引没问题还慢 → 考虑分页优化（深分页用延迟关联）、分库分表、加 Redis 缓存挡在前面

## 满分口述模板（第 2、3 题合并版）

"MySQL 索引用 B+ 树是层层淘汰的结果：哈希表等值查询快但不支持范围和排序；红黑树是二叉树，数据一多树高几十层，每层都是一次磁盘 IO 受不了；B 树每个节点都存数据，非叶子能容纳的索引少；B+ 树非叶子只存索引，一个 16K 的页能存上千个索引项，3~4 层就能覆盖千万级数据，而且叶子节点用链表相连，范围查询顺着链表扫就行。所以核心是两点：矮胖减少 IO，叶子链表利于范围查询。"
