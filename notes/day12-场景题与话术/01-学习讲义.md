## 一、场景题通用框架：秒杀系统设计 ⭐压轴大题

"设计一个秒杀系统"几乎必考。记住这个由浅入深的演进路线，边讲边"升级"：

### 第 1 层：把压力挡在数据库前面（最重要的一句话）

```
核心思想：数据库是瓶颈，凡是能不到数据库的，都别到数据库。
```

### 第 2 层：逐级拦截的流量漏斗

```
用户请求
  ↓ ① 前端：按钮置灰、答题/验证码（防机器人 + 打散请求时间）
  ↓ ② 网关层：限流（令牌桶，比如只放行 1000 QPS）
  ↓ ③ Redis：库存预热到 Redis，原子扣减（DECR / Lua 脚本）
  ↓     抢到的 → 发 MQ 消息
  ↓ ④ MQ（消息队列）：削峰，把"瞬间 10 万单"变成"匀速消费"
  ↓ ⑤ 消费者服务：慢慢落库（创建订单、扣真实库存）
  ↓ MySQL：只承受 MQ 消费者匀速来的压力
```

每一层都有话说：
- **Redis 预减库存**：内存操作，原子（DECR 或 Lua），扛住 10 万 QPS
- **MQ 削峰填谷**：洪峰先堆在队列里，消费者按自己的节奏处理，数据库不被打死
- **异步 + 轮询**：用户提交后先收到"排队中"，前端轮询结果，不傻等

### 第 3 层：还要考虑的细节（说出来就加分）

- **防超卖**：Redis 原子扣减兜底 + 数据库 `stock > 0` 条件更新双保险（Day 10 学的）
- **防重复下单（幂等）**：同一用户同一商品只能买一单 → 数据库唯一索引 `(user_id, product_id)` 或 Redis `SETNX user:1:product:2`
- **库存预热**：活动开始前把库存从 DB 加载到 Redis
- **降级兜底**：Redis 挂了 → 直接拒单/排队页，不能放流量打 DB

## 二、MQ（消息队列）概念篇 ⭐高频

时间紧，MQ 以**概念口述**为主，不要求搭环境实操。

### 为什么用 MQ？三大用途

| 用途 | 例子 |
|---|---|
| **异步** | 下单后发短信：不用等短信发完才返回，扔个消息就走 |
| **削峰** | 秒杀：洪峰堆队列，匀速消费 |
| **解耦** | 订单系统不用知道积分/物流/短信系统的存在，发消息就行 |

### 三大经典问题（必考）

**① 消息丢失怎么办？** —— 三个环节都可能丢，逐个堵：
- 生产者 → MQ：**发送确认机制**（confirm），失败重发
- MQ 自身：**持久化**（消息落盘，集群多副本）
- MQ → 消费者：**手动 ack**，业务处理完再确认；处理失败重回队列

**② 重复消费怎么办？（幂等性）**
- MQ 保证"至少一次"投递，重复是常态，**消费者必须自己保证幂等**
- 手段：业务唯一键 + 数据库唯一索引 / Redis SETNX 去重表

**③ 消息顺序性？**
- 全局有序很难；通常保证**局部有序**：同一订单的消息路由到同一个队列、同一个消费者按序处理

### 主流 MQ 一句话对比

- **RocketMQ**：阿里系，Java 写的，功能全（延迟消息、事务消息），互联网常用
- **Kafka**：吞吐量之王，日志/大数据场景
- **RabbitMQ**：erlang 写的，延迟低功能全，中小规模常用

## 三、分布式事务概念篇（知道方案名字 + 适用场景即可）

跨服务的数据一致性（订单服务扣库存、账户服务扣钱，怎么保证一起成功/失败）：

| 方案 | 思路 | 适用 |
|---|---|---|
| **2PC/XA** | 两阶段提交：先都"预备"，再统一提交 | 强一致但性能差，很少用 |
| **TCC** | Try（预留资源）→ Confirm（确认）→ Cancel（取消） | 资金类强一致场景 |
| **本地消息表** | 本地事务里同时写业务表 + 消息表，后台轮询消息表投递 | 最终一致，常用 |
| **MQ 事务消息** | 先发半消息，本地事务成功后确认 | 最终一致，RocketMQ 支持 |
| **Seata** | AT 模式框架，自动生成回滚日志 | 想快速接入时 |

> 面试话术："跨服务强一致代价很大，实际项目大多接受**最终一致性**，用本地消息表或 MQ 事务消息实现，配合重试和对账兜底。"

## 四、paismart 项目话术（STAR 法则）⭐

STAR = Situation 背景 → Task 任务 → Action 行动 → Result 结果。讲项目最忌平铺直叙"我用了 XX 技术"，要讲**你解决了什么问题**。

### 模板（按这个结构，填入你自己的真实细节）

```
【S 背景】我做的 paismart 是一个企业级 AI 知识库系统，解决企业文档分散、
        员工查找知识效率低的问题。

【T 任务】我负责后端部分，核心挑战是：____（比如：文档检索慢 / 知识库问答
        需要结合大模型 / 权限控制复杂）。

【A 行动】我做了什么：
        1. 技术选型：____（Spring Boot + ____ + 向量数据库/ES + ____）
        2. 遇到的最大的坑：____（必须想一个！比如：检索结果不准、
           并发上传文档冲突、大模型响应慢）
        3. 怎么解决的：____（把 Day 7-11 学的东西对上号！缓存/索引/异步）

【R 结果】量化结果：检索从 X 秒优化到 X 秒 / 支撑了 X 用户 / X 份文档
```
