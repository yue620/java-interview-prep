## 〇、先搞懂：线程是什么？为什么要学它？

**类比**：程序是一家餐厅。

- **进程** = 整个餐厅（有自己的厨房、桌椅、账本 → 内存空间）
- **线程** = 餐厅里的**服务员**。一个餐厅可以有多个服务员同时干活，他们**共用**厨房和账本（同一个进程的内存）

单线程程序 = 只有一个服务员：点单、做菜、上菜全一个人干，客人多了就排队。

多线程 = 多个服务员同时干活，**快**——但麻烦也来了：两个服务员同时改同一本账（共享变量），账就乱了。**并发编程学的就是"怎么让多个服务员干活又快又不乱"**。

Java 面试问并发，就是在问：你知道账本会乱吗？你知道怎么防吗（锁）？防的工具都有哪些坑吗？

## 一、创建线程：从"能跑起来"开始

### 1.1 先感受：不用线程 vs 用线程

**示例 1：单线程——两件事只能先后做**

```java
public class SingleThread {
    public static void main(String[] args) {
        for (int i = 0; i < 3; i++) {
            System.out.println("做菜 " + i);
        }
        for (int i = 0; i < 3; i++) {
            System.out.println("上菜 " + i);
        }
    }
}
```

输出（一定是这个顺序）：

```
做菜 0
做菜 1
做菜 2
上菜 0
上菜 1
上菜 2
```

**示例 2：多线程——两件事"同时"做**

```java
public class MultiThread {
    public static void main(String[] args) {
        // 创建一个新线程去"做菜"
        new Thread(() -> {
            for (int i = 0; i < 3; i++) {
                System.out.println("做菜 " + i);
            }
        }).start();

        // 主线程继续"上菜"
        for (int i = 0; i < 3; i++) {
            System.out.println("上菜 " + i);
        }
    }
}
```

输出（**每次运行顺序都不一样**，因为两个线程在交替执行）：

```
上菜 0
做菜 0
上菜 1
做菜 1
做菜 2
上菜 2
```

> 看到"输出顺序每次不同"，你就直观理解了并发：**两个线程谁先谁后由操作系统调度，不受你控制**。这既是多线程快的原因，也是一切 bug 的根源。

### 1.2 四种创建方式（逐个敲一遍）

**方式 ①：继承 Thread**

```java
class CookThread extends Thread {
    @Override
    public void run() {                    // 线程要干的活写在 run() 里
        System.out.println("新线程在做菜");
    }
}

public class Way1 {
    public static void main(String[] args) {
        new CookThread().start();          // start() 才真正启动新线程
    }
}
```

**方式 ②：实现 Runnable（推荐）**

```java
public class Way2 {
    public static void main(String[] args) {
        Runnable task = () -> System.out.println("新线程在做菜");  // lambda 简写
        new Thread(task).start();
    }
}
```

**方式 ③：Callable + FutureTask（能拿返回值）**

```java
import java.util.concurrent.*;

public class Way3 {
    public static void main(String[] args) throws Exception {
        Callable<Integer> task = () -> {
            Thread.sleep(1000);        // 假装算了 1 秒
            return 42;                 // Callable 可以有返回值！
        };

        FutureTask<Integer> ft = new FutureTask<>(task);
        new Thread(ft).start();

        System.out.println("主线程先干别的...");
        Integer result = ft.get();     // 阻塞在这里，等新线程算完
        System.out.println("拿到结果：" + result);
    }
}
```

输出：

```
主线程先干别的...
（等约 1 秒）
拿到结果：42
```

**方式 ④：线程池（先混个眼熟，Day 4 细讲）**

```java
import java.util.concurrent.*;

public class Way4 {
    public static void main(String[] args) {
        ExecutorService pool = Executors.newFixedThreadPool(2);
        pool.submit(() -> System.out.println("池里的线程在干活"));
        pool.shutdown();
    }
}
```

### 1.3 必考陷阱：start() 和 run() 的区别

**示例 3：亲自验证区别**

```java
public class StartVsRun {
    public static void main(String[] args) {
        Thread t = new Thread(() -> {
            System.out.println("run 方法运行在: " + Thread.currentThread().getName());
        }, "我的新线程");

        t.run();     // 直接调 run()
        t.start();   // 调 start()
    }
}
```

输出：

```
run 方法运行在: main        ← 直接调 run()，是 main 线程在执行！没有新线程！
run 方法运行在: 我的新线程   ← start() 才真正创建了新线程
```

> **面试答案**：`start()` 让 JVM 创建一个新线程去执行 run()；直接调 `run()` 只是当前线程里的普通方法调用，和并发没有半点关系。另外 start() 一个线程只能调一次，调两次抛 `IllegalThreadStateException`——一个 Thread 对象只能启动一次，线程结束了也不能复活；想再跑同样的任务，用同一个 Runnable 新建一个 Thread。

### 1.4 Runnable vs Callable（背这张表）

| | Runnable | Callable |
|---|---|---|
| 方法 | `run()` | `call()` |
| 返回值 | **没有** | **有** |
| 能抛受检异常 | 不能（方法签名没有 throws） | 能 |
| 怎么用 | 直接传给 Thread | **必须先包一层 FutureTask** 才能给 Thread |

> 为什么 Callable 不能直接 `new Thread(callable)`？因为 Thread 的构造方法只收 Runnable。FutureTask 同时实现了 Runnable 和 Future 接口——既能 start，又能 get() 拿结果，它是个"转换器"。

### 1.5 为什么推荐实现 Runnable 而不是继承 Thread？（高频题）

**三条理由，从浅到深**：

**① Java 单继承，继承名额很宝贵**

```java
class MyTask extends Thread { }   // ❌ 用掉了唯一的继承名额，以后不能继承别的类了
class MyTask implements Runnable { }  // ✅ 接口想实现几个都行，还能自由继承业务基类
```

**② 任务和线程解耦（组合优于继承）**

```java
// 继承 Thread：活焊死在工人身上，这个工人只会干这个
class CookThread extends Thread { public void run() { 做菜 } }

// 实现 Runnable：活是独立的，谁都能干，还能复用
Runnable cookTask = () -> 做菜;
new Thread(cookTask).start();    // 工人 A 干
new Thread(cookTask).start();    // 工人 B 也干（同一个任务！）
```

**③ 线程池只收任务不收工人（最现实的理由）**

```java
pool.submit(Runnable task);   // 线程池只收 Runnable / Callable
// 没有 pool.submit(Thread) —— 继承 Thread 的写法进不了池子
```

生产环境用线程池复用线程（几个固定工人轮流干源源不断的活），任务必须和线程分开才有得复用。

> 追问准备："Thread 本身和 Runnable 什么关系？"——Thread 类本身就 `implements Runnable`，继承 Thread 重写 run() 本质上还是在填 Runnable 的 run，只是顺便把任务和线程耦合在了一起。

## 二、线程的生命周期：六种状态

### 2.1 六种状态总览

一个线程从创建到死亡，会在这六种状态之间流转：

```
        start()
新建 ──────────→ 运行中（RUNNABLE，包含"就绪"和"正在跑"）
(NEW)               │
                    ├── 抢 synchronized 锁失败 ──→ 阻塞（BLOCKED）
                    ├── wait() / join() 无时限等待 ──→ 等待（WAITING）
                    ├── sleep(ms) / wait(ms) 有时限等待 ──→ 超时等待（TIMED_WAITING）
                    └── run() 执行完 ──→ 终止（TERMINATED）
```

| 状态 | 含义 | 餐厅类比 |
|---|---|---|
| NEW | new 了 Thread 但还没 start | 服务员已入职，还没上班 |
| RUNNABLE | 在干活或随时能上 | 正在餐厅里忙活 |
| **BLOCKED** | **抢锁失败**，在锁门口等着 | 结账台有人，堵在门口 |
| **WAITING** | **wait()/join()**，无限期等别人叫 | 进等待室，等厨师喊"菜好了" |
| **TIMED_WAITING** | **sleep(ms)/wait(ms)**，到点自己醒 | 定好闹钟眯一会儿 |
| TERMINATED | run() 跑完了 | 下班了 |

### 2.2 高频追问：BLOCKED 和 WAITING 怎么区分？（必考）

这俩都是"线程停住了"，但原因完全不同：

- **BLOCKED**：想进 synchronized 但**锁被别人占着**——它是"**想干活但进不了门**"，拿到锁就自动回到 RUNNABLE
- **WAITING**：自己主动调了 `wait()` 放弃锁——它是"**条件没到，我主动等**"，必须有人 `notify()` 才可能继续

### 2.3 示例 4：亲手"看到"各种状态

```java
public class StateDemo {
    static final Object lock = new Object();

    public static void main(String[] args) throws InterruptedException {
        // 线程 A：先抢锁，抱着锁睡 3 秒
        Thread a = new Thread(() -> {
            synchronized (lock) {
                try { Thread.sleep(3000); } catch (InterruptedException e) { }
            }
        }, "线程A");

        // 线程 B：也要抢同一把锁
        Thread b = new Thread(() -> {
            synchronized (lock) {
                System.out.println("B 终于拿到锁了");
            }
        }, "线程B");

        System.out.println("启动前 B 的状态: " + b.getState());   // NEW

        a.start();
        b.start();
        Thread.sleep(500);   // 确保 A 已拿锁睡着，B 已去抢锁

        System.out.println("A 睡觉时的状态: " + a.getState());    // TIMED_WAITING
        System.out.println("B 抢锁时的状态: " + b.getState());    // BLOCKED

        a.join();
        b.join();
        System.out.println("结束后 B 的状态: " + b.getState());   // TERMINATED
    }
}
```

输出：

```
启动前 B 的状态: NEW
A 睡觉时的状态: TIMED_WAITING    ← sleep：有时限等待，还抱着锁
B 抢锁时的状态: BLOCKED          ← 锁被 A 占着，B 堵在门口
结束后 B 的状态: TERMINATED
```

> `Thread.getState()` 可以随时查看线程状态——明天的死锁实验里，jstack 报告就是用这些状态词描述的，先混个脸熟。

## 三、共享变量会"乱"成什么样（学锁之前先看灾难现场）

**示例 5：两个服务员同时记账——账乱了**

```java
public class RaceDemo {
    static int count = 0;   // 共享的账本

    public static void main(String[] args) throws InterruptedException {
        Runnable add = () -> {
            for (int i = 0; i < 10000; i++) {
                count++;    // 两个线程都在对同一个 count +1
            }
        };

        Thread t1 = new Thread(add);
        Thread t2 = new Thread(add);
        t1.start();
        t2.start();
        t1.join();          // join = 等 t1 干完
        t2.join();          // 等 t2 干完

        System.out.println("期望 20000，实际: " + count);
    }
}
```

输出（**每次都不一样，而且几乎总是小于 20000**）：

```
期望 20000，实际: 17352
```

**为什么少了？** `count++` 看着是一行，实际是**三步**：

```
1. 读 count 的值
2. +1
3. 写回 count
```

两个线程交错执行时就出事：

```
count 现在是 100
线程A：读到 100
线程B：读到 100      ← A 还没写回，B 也读了 100
线程A：+1 写回 101
线程B：+1 写回 101   ← B 也写 101！两次 +1 只涨了 1，丢了一次
```

> 这种现象叫**竞态条件（race condition）**，这种"读-改-写"三步操作叫**非原子操作**。记住这个示例——它是后面 synchronized、volatile、AtomicInteger 存在的全部理由。

## 四、synchronized：给账本配一把锁

### 4.1 一句话理解

synchronized = **一次只允许一个线程进入**的"单人结账台"。谁拿到锁谁进去改账，别人在门口排队（阻塞 → 就是上面的 BLOCKED 状态）。

**示例 6：用 synchronized 修复示例 5**

```java
public class SyncDemo {
    static int count = 0;
    static final Object lock = new Object();   // 专门用来当锁的对象

    public static void main(String[] args) throws InterruptedException {
        Runnable add = () -> {
            for (int i = 0; i < 10000; i++) {
                synchronized (lock) {   // 进结账台：一次只进一个线程
                    count++;
                }                       // 出来：锁自动还给下一个人
            }
        };

        Thread t1 = new Thread(add);
        Thread t2 = new Thread(add);
        t1.start(); t2.start();
        t1.join();  t2.join();

        System.out.println("期望 20000，实际: " + count);
    }
}
```

输出（**这次永远是 20000**）：

```
期望 20000，实际: 20000
```

### 4.2 三种用法——锁的对象分别是谁（必考）

```java
synchronized (lock) { }              // ① 代码块：锁你指定的对象（最灵活）

public synchronized void m() { }     // ② 实例方法：锁 this（当前对象）

public static synchronized void sm() { }  // ③ 静态方法：锁 这个类的 Class 对象（全局一把锁）
```

**示例 7：证明"锁不同对象 = 没锁"**

```java
public class WrongLock {
    static int count = 0;

    public static void main(String[] args) throws InterruptedException {
        Runnable add = () -> {
            for (int i = 0; i < 10000; i++) {
                synchronized (new Object()) {  // ❌ 每次 new 一把新锁！
                    count++;                    //    等于没锁
                }
            }
        };
        Thread t1 = new Thread(add);
        Thread t2 = new Thread(add);
        t1.start(); t2.start();
        t1.join();  t2.join();
        System.out.println("实际: " + count);   // 又不到 20000 了
    }
}
```

> **核心认知**：锁要有效，所有线程必须抢**同一把**锁。示例 6 里 `lock` 是 static 的、全程序只有一个，所以有效；示例 7 每次 new 一把，各进各的门，形同虚设。

### 4.3 锁升级：JVM 的"看人下菜碟"（理解版）

重量级锁（让线程排队睡觉）要进出操作系统内核，**很贵**——贵在**阻塞和唤醒要切换内核态**，一次切换比同步代码本身执行还慢。JVM 观察发现：现实中很多锁根本没竞争。于是它把锁分成四档，**从轻到重逐步升级**：

```
无锁 → 偏向锁 → 轻量级锁 → 重量级锁
       （只能升级，不能降级；锁状态记录在对象头的 MarkWord 里）
```

用"单人结账台"类比：

| 锁状态 | 场景 | 类比 |
|---|---|---|
| **偏向锁** | 一直只有同一个线程来 | 常客来了直接进，门口记一下他的名字，之后进出零成本 |
| **轻量级锁** | 偶尔有第二个人来，但错得开 | 门口稍等转两圈（**自旋**），里面的人马上出来，不用排队睡觉 |
| **重量级锁** | 一堆人挤着抢 | 排队取号睡觉（**阻塞**），轮到你了操作系统叫醒你 |

> **面试一句话**：JDK6 后 synchronized 做了锁升级优化：无竞争时偏向锁零开销，轻竞争时自旋不阻塞，真激烈才升级成重量级锁进内核态排队。**设计动机是省"线程阻塞/唤醒的内核态切换开销"，不是省内存**。这也是 StringBuffer 单线程下不慢的原因——锁停在轻量级。

### 4.4 sleep 和 wait 的区别（必考，用示例感受）

**示例 8：sleep 抱着锁睡觉**

```java
public class SleepHoldLock {
    static final Object lock = new Object();

    public static void main(String[] args) {
        Runnable r = () -> {
            synchronized (lock) {
                System.out.println(Thread.currentThread().getName() + " 拿到锁，睡 2 秒");
                try {
                    Thread.sleep(2000);     // 睡觉，但锁还抱在怀里！
                } catch (InterruptedException e) { }
                System.out.println(Thread.currentThread().getName() + " 醒了，放锁");
            }
        };
        new Thread(r, "线程A").start();
        new Thread(r, "线程B").start();
    }
}
```

输出（注意：**B 一定等 A 睡完 2 秒放锁后才能进去**）：

```
线程A 拿到锁，睡 2 秒
（等 2 秒）
线程A 醒了，放锁
线程B 拿到锁，睡 2 秒     ← B 被挡了整整 2 秒
（等 2 秒）
线程B 醒了，放锁
```

> **五维度对比（面试直接背）**：
> ① 归属：sleep 是 Thread 静态方法，wait 是 Object 方法（所以是 `lock.wait()`）
> ② 位置：sleep 哪都能用，wait 必须在 synchronized 里（否则抛 IllegalMonitorStateException）
> ③ 锁：sleep **不放锁**，wait **释放锁**
> ④ 唤醒：sleep 到点自动醒，wait 要靠 notify/notifyAll 叫醒**并且重新抢到锁**
> ⑤ 用途：sleep 是单纯延时，wait/notify 是线程间协调（等条件，比如生产者消费者）

## 五、volatile：一块"公告栏"

### 5.1 解决什么问题：你看不到我改的

CPU 为了快，每个核有自己的**缓存**。线程读变量可能读的是自己缓存里的旧值，另一个线程改了主存里的值，它看不见。

**示例 9：可见性问题（没有 volatile）**

```java
public class VisibilityDemo {
    static boolean running = true;   // 注意：没加 volatile

    public static void main(String[] args) throws InterruptedException {
        new Thread(() -> {
            System.out.println("子线程开始转圈，等 running 变 false");
            while (running) { }       // 一直读缓存里的 true，可能永远出不来
            System.out.println("子线程结束");
        }).start();

        Thread.sleep(1000);
        running = false;              // main 线程改了值
        System.out.println("main 已把 running 改为 false");
    }
}
```

可能的输出（**子线程那行"结束"可能永远不打印，程序卡死**）：

```
子线程开始转圈，等 running 变 false
main 已把 running 改为 false
（子线程还在读自己缓存里的 true，转圈到天荒地老……）
```

**修复**：`static volatile boolean running = true;`

加上 volatile 后：写的人**立刻把新值刷到主存**，读的人**每次都从主存读**——像一块公告栏，谁写了大家都看见。再跑示例 9，子线程 1 秒后正常结束。

### 5.2 volatile 管不了的：原子性（必考陷阱）

把示例 5 的 `count` 加上 volatile 再跑：

```java
static volatile int count = 0;   // 加了 volatile
// ... 两个线程各 count++ 一万次 ...
System.out.println(count);       // 还是不到 20000！
```

**为什么**：`count++` 是"读→加→写"三步。volatile 只保证"读的时候看到最新值"，但两个线程可以**同时读到同一个最新值**，然后各加各的——丢更新照旧。

> **一句话**：volatile 管"看得见"（可见性），不管"一起改"（原子性）。要原子性还是得 synchronized 或 AtomicInteger。

### 5.3 应用：双重检查锁单例（DCL）

**示例 10：能直接用的单例**

```java
public class Singleton {
    // ① volatile 必须有！原因见下
    private static volatile Singleton instance;

    private Singleton() { }   // 私有构造，别人 new 不了

    public static Singleton getInstance() {
        if (instance == null) {                    // ② 第一次检查：不为 null 就直接返回（不用抢锁，快）
            synchronized (Singleton.class) {       // ③ 抢锁
                if (instance == null) {            // ④ 第二次检查：可能等锁期间别人已经建好了
                    instance = new Singleton();    // ⑤ 只有真正第一个进来的线程会执行到这
                }
            }
        }
        return instance;
    }
}
```

**三个"为什么"（面试连环问）**：

1. **为什么要检查两次？** 第一次检查挡掉 99% 的调用（建好之后进来直接返回，不用抢锁）；第二次检查防"两个线程同时通过第一次检查，排队等锁，都进去 new"。
2. **为什么 volatile 不能省？** `new Singleton()` 实际三步：分配内存 → 初始化 → 引用指向内存。JVM 可能重排成"分配 → 指向 → 初始化"。这时另一个线程第一次检查发现引用不为 null，**直接返回了一个还没初始化的半成品对象**。volatile 禁止这种重排。
3. **构造为什么私有？** 不然别人随便 new，单例形同虚设。

**单例的用途**（面试问"哪里用"）：配置管理器、线程池/连接池、全局计数器、缓存——凡是"全局唯一资源的管理者"都该单例。Spring 的 Bean 默认就是单例（IoC 容器实现，不用手写 DCL）。

## 六、本日知识地图（复述用）

```
为什么学并发：共享变量 + 非原子操作(count++) = 丢数据（示例 5 的灾难现场）

线程
├── 创建 4 法：继承Thread / 实现Runnable / Callable(有返回值) / 线程池
├── 推荐 Runnable 三理由：单继承限制 / 任务线程解耦 / 线程池只收任务
├── start() 才开新线程；直接 run() 是普通调用；start 只能调一次
├── 六状态：NEW/RUNNABLE/BLOCKED(抢锁失败)/WAITING(wait主动等)/TIMED_WAITING(sleep)/TERMINATED
└── sleep 抱着锁睡 vs wait 交出锁等通知（五维度对比）

synchronized
├── 本质：一次只进一个线程的"单人结账台"（示例 6 修好了账本）
├── 三种用法：锁指定对象 / 锁 this / 锁 Class
├── 铁律：必须锁同一个对象才有效（示例 7 反例）
└── 锁升级：无锁→偏向→轻量(自旋)→重量(阻塞)，只升不降，记在 MarkWord

volatile
├── 公告栏：可见性（示例 9：不加会死循环）+ 禁指令重排
├── 不管原子性：volatile 的 count++ 照样丢数据
└── DCL 单例：两次检查 + volatile 防半成品对象

synchronized vs volatile（高频对比题）
├── synchronized：原子性+可见性，会阻塞，能修饰方法/代码块
└── volatile：只保证可见性+禁重排，不阻塞，只能修饰变量，更轻量
```
