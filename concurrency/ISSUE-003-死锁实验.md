# ISSUE-003：死锁复现、jstack 排查与修复

> 阶段 2 · Day 3（8/14）实践任务
> 对应八股：synchronized、死锁四条件、线程状态
> 产出：一份能讲给面试官听的完整排查记录（面试场景题"你怎么排查死锁"的标准答案）

---

## 一、需求描述

死锁是并发面试的必考题，但 90% 的人只会背"四个条件"。本任务要求你走完**完整的实战闭环**：亲手写出死锁 → 用 JDK 自带的 `jstack` 工具抓到它 → 分析工具输出 → 修复 → 验证。面试被问"线上出现死锁你怎么排查"，你就讲今天这个流程。

## 二、任务步骤

### 任务 1：写出死锁（`concurrency/DeadlockDemo.java` 骨架已给）

两个线程、两把锁，互相等对方：

```
线程1：锁 A 到手 → 想拿锁 B
线程2：锁 B 到手 → 想拿锁 A
```

**验收**：程序运行后卡死（永远不会自己结束），两个线程都打印不出"完成"。

### 任务 2：用 jstack 抓死锁

程序卡死时，**不要关窗口**，另开一个终端：

```bash
# 1. 找到 Java 进程号
jps -l

# 2. 抓线程快照（把 <pid> 换成上一步的数字）
jstack <pid>
```

**验收**：在输出末尾找到 jstack 自动检测到的死锁报告，类似：

```
Found one Java-level deadlock:
=============================
"Thread-1":
  waiting to lock monitor 0x... (object 0x..., a java.lang.Object),
  which is held by "Thread-0"
...
```

**把这段报告完整复制到 DeadlockDemo.java 的类注释里留证**，并在注释里回答：报告里哪两行说明了"互相持有对方要的锁"？

### 任务 3：修复死锁

用**固定加锁顺序**修复：两个线程都按 A → B 的顺序拿锁。

**验收**：修复后程序正常运行结束，两个线程都打印"完成"。

### 任务 4：写排查总结（面试话术）

在类注释末尾写 3~5 行总结，模板：

```
线上排查死锁流程：
1. 发现服务无响应/CPU 异常
2. jps 找进程号 → jstack <pid> 抓线程快照
3. 找 "Found one Java-level deadlock" 或大量 BLOCKED 线程
4. 定位到互相等待的代码行，用固定加锁顺序/超时锁修复
（结合你自己的实验补一句心得）
```

## 三、思考题（注释里回答）

1. 死锁的四个必要条件是什么？你的修复破坏了其中哪一个？
2. 除了固定加锁顺序，你还知道哪些避免死锁的手段？（提示：tryLock 超时）
3. jstack 输出里线程状态显示为什么？（呼应讲义 §二的生命周期）

## 四、环境提示

- `jps` 和 `jstack` 在 JDK 的 bin 目录里，IDEA 用的 JDK 就自带。如果终端找不到命令，去 IDEA 的 `File → Project Structure → SDKs` 看你的 JDK 路径，用完整路径调用，如 `"C:\...\jdk-17\bin\jstack.exe" <pid>`
- 也可以在 IDEA 运行窗口的**进程名上右键**找线程 dump 功能，但建议至少用一次命令行——面试讲的是命令行流程
